# Remediation Requirements — SRP-1 / Target v0.3.3

## REQ-01 — OS isolation and safe execution (AUD-01, AUD-14, AUD-17)
- Sensitive shell execution MUST run inside a real OS-enforced isolation boundary.
- An adapter MUST declare per-capability support truthfully; controller MUST evaluate `supportsCapability()` or an equivalent authoritative capability contract.
- Process group/job termination alone MUST NOT be accepted as filesystem/network isolation.
- If a required isolation feature is unavailable, unsupported, or fails initialization, execution MUST be denied.
- Add platform-specific negative tests proving access to host sentinel files and disallowed network endpoints is blocked.
- If complete isolation cannot be delivered for a platform in this patch, disable sensitive shell execution on that platform and document the restriction.

## REQ-02 — Mandatory identity and policy evaluation (AUD-02, AUD-04, AUD-10)
- Every agent-originated sensitive action MUST include authenticated session and bot principal.
- Missing identity MUST deny.
- Bot-bound grant MUST match exact authenticated bot ID; missing bot ID is not a wildcard.
- Messaging service MUST resolve sender identity from trusted session/runtime context, not caller-supplied string alone.
- Unknown/inactive senders MUST be rejected; human/system principals require explicit typed identity.

## REQ-03 — Canonical capability scope and persistence safety (AUD-03, AUD-05)
- Validate session identifiers before constructing any filesystem path.
- Resolve canonical workspace and destination paths; prove containment using platform-correct semantics.
- Case sensitivity MUST follow filesystem/platform semantics; do not lowercase paths universally.
- Reject ambiguous, unresolved, or out-of-scope paths.
- Add traversal, mixed-case, symlink, junction, and platform-specific tests.

## REQ-04 — Inbox delivery correctness (AUD-06, AUD-08)
- Apply filters and limit before changing read/delivery state.
- `readInbox` MUST NOT mark messages outside the returned page as read.
- Worker ACK/fail MUST require current lease owner and valid fencing token.
- Stale workers MUST NOT alter a message reclaimed by another worker.
- Administrative override MUST be a separate explicit API with audit.

## REQ-05 — Broadcast delivery correctness (AUD-07)
- Choose and document one model: durable per-consumer delivery/ack, or independent per-category cursors.
- Cursor MUST NOT advance before successful processing/acknowledgment.
- Filtering and pagination MUST NOT skip events outside the requested category.
- Callback failure and process restart MUST allow redelivery.
- Tests MUST cover mixed categories, limits, callback failure, and restart.

## REQ-06 — Lock and storage fencing (AUD-09)
- Lock acquisition, stale recovery, release, and renewal MUST be ownership-safe and race-tested.
- A fencing token MUST be validated by the protected storage write boundary, not merely generated by the lock manager.
- A stale holder MUST be unable to commit after a newer lease/fencing epoch is active.
- If the underlying filesystem cannot provide required atomic semantics, use a safer storage/coordination mechanism or fail closed.

## REQ-07 — Secret lifecycle and redaction (AUD-11)
- Normal CLI operation MUST NOT accept API secrets through process argv.
- Deprecate/remove `--api-key`; if a transition flag remains, it MUST be explicitly unsafe, disabled by default, and excluded from documented examples.
- A centralized recursive redactor MUST run before work log, Blackboard, security audit, messaging metadata, exceptions, telemetry, and CLI output.
- Register provider secrets at provider initialization and remove them on provider disposal.
- Canary tests MUST search all persistence/output artifacts for raw secrets, including nested object fields and common token formats.

## REQ-08 — Approval workflow (AUD-12)
- Per-action approval MUST call a trusted human approval interface and record approver, decision, scope, timestamp, and action.
- If no trusted approval interface is available, grant creation MUST reject `per_action` for the unsupported operation; do not accept a grant that can never be used.

## REQ-09 — Capability preset and enforcement consistency (AUD-13, AUD-14)
- Every preset MUST be evaluated end-to-end against actual controller operations.
- Preset descriptions MUST state exact grants/scopes; no implicit wildcard scope unless explicitly approved and safely bounded.
- A registered but unenforced capability MUST return unsupported/deny.
- Add table-driven tests for all presets and all capability types.

## REQ-10 — Prompt trust boundary (AUD-15)
- Serialize untrusted peer messages as structured data or escape all delimiter/control sequences before prompt insertion.
- Delimiters are defense-in-depth, not an authorization boundary.
- Add adversarial tests with embedded closing markers, nested markers, newlines, and instruction-like content.

## REQ-11 — Mandatory security audit durability (AUD-16)
- Grant/revoke and sensitive execution events require durable audit.
- If mandatory audit cannot be persisted, protected action MUST fail closed.
- Use transaction/outbox/recovery design to avoid grant success without corresponding audit record.
- Audit records MUST pass through central redaction.

## REQ-12 — Cancellation propagation (AUD-20)
- Runtime MUST own an AbortController per bot operation or equivalent lifecycle.
- Signal MUST propagate through agent loop, provider call, retry wait, and shutdown.
- Stop/shutdown MUST abort in-flight provider requests and waits.
- Tests MUST prove prompt cancellation and no post-stop retry.

## REQ-13 — Documentation, IDs, and release hygiene (AUD-18, AUD-19)
- AUD-01–AUD-20 are canonical and immutable identifiers.
- Requirements, phases, test names, changelog, open issues, and reports MUST use the same mapping.
- Regenerate lockfile using the target package version and verify package metadata consistency.
- Source archives MUST exclude `.git` and `node_modules`; use lockfile for reproducible installation.
- Remove duplicate/stale documentation or designate a single canonical report location.

## Global acceptance criteria
- No Critical/High finding remains open for release.
- All supported platform isolation claims have executable negative tests.
- Missing identity/context and unavailable enforcement fail closed.
- Every finding maps to requirement, code change, regression test, and evidence.
- Clean install, build, full test suite, and security regression suite pass on supported OS matrix.
- Final report includes residual risks and explicit GO/NO-GO decision.
